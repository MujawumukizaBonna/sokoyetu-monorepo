# pawaPay Mobile Money Integration Spec

This document captures the pawaPay v2 integration needed to add Mobile Money payments for SokoYetu, including MTN and Airtel support where the merchant account and country configuration allow it.

## Scope

- Collect payment from a retailer using Mobile Money.
- Support provider selection for MTN and Airtel based on pawaPay configuration.
- Use pawaPay callbacks as the source of truth for final payment status.
- Update order/payment state in the backend only after payment is confirmed.
- Keep the current frontend checkout flow, but replace the current "paid on submit" behavior with a real payment request flow.

## What pawaPay Provides

pawaPay is an async Mobile Money API for paying and getting paid in Sub-Saharan Africa. The important integration points are:

- Bearer token authentication.
- Optional request and callback signing using RFC-9421.
- Deposit flow for collecting money from a customer.
- Payout flow for sending money to a customer.
- Toolkit endpoints for provider availability, active configuration, and provider prediction.
- Callback delivery for final payment state.

## Recommended Flow For SokoYetu

For the current product, the primary use case is `deposit`:

1. Retailer confirms checkout.
2. Frontend sends checkout details to backend.
3. Backend creates a pawaPay deposit request.
4. Customer authorizes the payment on their phone if required by the provider.
5. pawaPay sends a callback with the final status.
6. Backend updates the local order record to `paid` only after the callback or a status check confirms completion.

## Deposit API Details

### Endpoint

- `POST /v2/deposits`

### Request fields

Required:

- `depositId`: UUIDv4 unique payment ID generated by us.
- `amount`: string amount.
- `currency`: ISO 4217 currency code.
- `payer.type`: should be `MMO`.
- `payer.accountDetails.phoneNumber`: MSISDN in international format.
- `payer.accountDetails.provider`: provider code such as `MTN_MOMO_RWA` or `AIRTEL_RWA` when supported.

Optional but useful:

- `clientReferenceId`: internal order reference.
- `customerMessage`: short transaction label.
- `metadata`: up to 10 metadata fields for reconciliation and reporting.
- `preAuthorisationCode`: only for providers that require pre-auth flows.

### Important deposit rules

- The request is idempotent by `depositId`.
- A duplicate `depositId` is ignored.
- Amounts must obey provider decimal rules and transaction limits.
- Not all providers support decimals.
- Leading zeros are not allowed except for values below 1.

### Initiation response statuses

- `ACCEPTED`: request accepted for processing.
- `REJECTED`: request rejected at initiation.
- `DUPLICATE_IGNORED`: duplicate request already accepted earlier.

### Final deposit statuses

- `COMPLETED`
- `FAILED`
- `PROCESSING` only for redirect-auth style providers

## Deposit Callback Handling

pawaPay sends the final deposit status to the configured callback URL.

Callback payload should be treated as the source of truth for payment completion.

Useful callback fields:

- `depositId`
- `status`
- `amount`
- `currency`
- `country`
- `payer`
- `created`
- `providerTransactionId`
- `customerMessage`
- `metadata`
- `failureReason` when failed

### Callback verification

If signed callbacks are enabled, validate:

- `Content-Digest`
- `Signature`
- `Signature-Input`
- `Signature-Date`

## Status Check Endpoint

Use polling only as a fallback or reconciliation tool.

- `GET /v2/deposits/{depositId}`
- Returns `FOUND` or `NOT_FOUND`
- If found, the `data` object contains the final payment state

## Provider Selection Strategy

For MTN and Airtel support, the provider should not be hardcoded in the UI.

Recommended flow:

1. Call active configuration for the relevant country and operation.
2. Show only the providers returned for that merchant account.
3. Optionally call predict-provider with the phone number to preselect the best match.
4. Allow the user to override the prediction.

### Toolkit endpoints to use

- `GET /v2/active-conf?country=<ISO3>&operationType=DEPOSIT`
- `GET /v2/availability?country=<ISO3>&operationType=DEPOSIT`
- `POST /v2/predict-provider`

### Example provider codes from the docs

The docs show examples such as:

- `MTN_MOMO_RWA`
- `AIRTEL_RWA`

The actual provider codes depend on the country and the merchant account configuration. We should always verify them with active configuration before using them in the app.

## MTN and Airtel Notes

The docs show both MTN and Airtel entries in the active configuration example for Rwanda. That means the integration should be designed to support multiple providers, not a single hardcoded network.

For the UI:

- show a provider dropdown or radio group
- do not default silently to one provider
- validate the phone number before payment submission

For the backend:

- store the provider code used for the payment
- store the pawaPay `depositId`
- map callback status to the local order payment state

## Suggested Database Changes

Reuse the existing `payments` table for pawaPay integration.

Suggested mapping:

- `payments.external_id` stores the pawaPay `depositId`
- `payments.payment_method` stores `mobile_money` or `pawapay_mobile_money`
- `payments.phone_number` stores the customer MSISDN
- `payments.status` stores:
  - `pending`
  - `processing`
  - `completed`
  - `failed`
  - `cancelled`
- `payments.provider_reference` stores the pawaPay `providerTransactionId`
- `payments.failure_reason` stores the failure reason when available

Keep `orders.payment_status` as a denormalized summary if the UI still needs it, but make `payments.status` the source of truth.

If you want to keep the schema changes minimal, the only likely addition is a clearer timestamp such as `paid_at` on `payments`.

## Suggested Backend Endpoints

### Create deposit

- `POST /api/payments/pawapay/deposit`

Backend responsibilities:

- validate order and customer details
- generate `depositId`
- create a row in `payments`
- choose provider code
- call pawaPay
- store the pawaPay deposit on the payment row
- return initiation status to the frontend

### Callback endpoint

- `POST /api/payments/pawapay/callback/deposit`

Backend responsibilities:

- verify optional signature headers
- find the matching payment by `depositId`
- update `payments.status`
- log provider transaction ID and failure reason
- mirror the result back to the related order if needed

### Optional status sync

- `GET /api/payments/pawapay/deposit/:depositId`

Backend responsibilities:

- query pawaPay status if callback is delayed
- reconcile local state

## Frontend Changes

Replace the current checkout-only submit with a payment form that includes:

- phone number
- provider selection
- optional country selector if multi-country support is planned
- payment status display

The existing `OrderSummary` screen is already a good place to initiate the flow, but it should wait for payment success before showing the final order confirmation.

## Payouts

Payouts are not needed for the current retail checkout flow, but the same pawaPay account can later be used to pay suppliers or customers.

Key payout endpoint:

- `POST /v2/payouts`

Useful for:

- supplier settlements
- customer refunds or reversals handled outside the order table

## Testing Notes

Use sandbox first.

The docs say:

- sandbox is isolated from production
- sandbox uses special test phone numbers
- sandbox does not show the actual PIN prompt flow

Check the docs for the latest test numbers and failure codes before implementing QA scenarios.

## Common Failure Cases To Handle

Technical errors:

- authentication errors
- invalid input
- missing or unsupported parameters
- invalid amount
- invalid phone number
- invalid currency
- invalid provider
- provider temporarily unavailable

Transaction failures:

- customer did not approve payment
- insufficient balance
- customer wallet/provider mismatch
- wallet limit reached
- unspecified failure

## Implementation Order

1. Add a payment table or extend the order table for deposit tracking.
2. Create pawaPay service helpers in the backend.
3. Add deposit initiation endpoint.
4. Add callback endpoint.
5. Update order payment status transitions.
6. Update checkout UI to collect provider and phone number.
7. Add sandbox test coverage and reconciliation handling.

## Acceptance Criteria

- Retailer can choose MTN or Airtel where available.
- Payment is not marked as paid until pawaPay confirms completion.
- Backend stores `depositId` for every payment.
- Callback updates the order status reliably.
- Failed and duplicate deposit requests are handled gracefully.
- Sandbox can be used without touching production credentials.
